# ทำไม NEW EYES อ่านผิด และแก้อย่างไร (รายงานผลการทดลอง)

**สรุป:** ปัญหาหลักไม่ได้อยู่ที่ตัว TTS แต่อยู่ที่ภาพที่ส่งเข้า OCR และจังหวะที่ระบบเลือกอ่าน
TTS อ่านตามที่ OCR ส่งมาทุกตัวอักษร ถ้า OCR อ่านผิดหรือได้ขยะ เสียงที่ออกมาก็จะผิดตาม

| | ก่อนแก้ | หลังแก้ |
|---|---|---|
| ความผิดพลาดระดับตัวอักษร (CER) ทุกสถานการณ์ | 46.4% | **12.4%** |
| ภาพที่ฟังแล้วเข้าใจ (CER ≤ 10%) | 35% | **82%** |
| ถ้าไม่นับตอนมือสั่น | – | CER **3.4%**, เข้าใจ **91%** |
| ภาพที่ OCR คืนค่าว่าง ทั้งที่มีตัวหนังสือ | 27% | **0%** |
| อ่านอัตโนมัติ: หน้าที่อ่านถูก (20 หน้า) | 5 | **17** |
| อ่านอัตโนมัติ: พูดข้อความมั่ว | 6 ครั้ง | **0 ครั้ง** |

ตัวเลข "หลังแก้" ได้จากการรัน `docs/preprocess.js` ตัวเดียวกับที่เว็บใช้จริง (`validate_js.mjs`)

## วิธีทดลอง

ไม่มีกล้องจริงให้ทดสอบ จึง **จำลองภาพจากกล้องมือถือ** (`sim.py`) แล้วรัน **Tesseract.js 5.1.1 ตัวเดียวกับในเว็บ** (`ocr.mjs`)

- **ข้อความ 10 ชุด** (`samples.json`): หนังสือเรียน ป้าย ฉลากยา ราคา/วันหมดอายุ ภาษาอังกฤษ และไทยปนอังกฤษ
  ใช้ฟอนต์ TH Sarabun New, Angsana, Leelawadee, Tahoma, Arial และ Times
  เรนเดอร์ด้วย Skia ซึ่งวางสระและวรรณยุกต์ไทยถูกตำแหน่ง (Pillow ทำไม่ได้)
- **10 สถานการณ์**: ปกติ / กล้อง 640×480 / 720p / เงาพาด / แสงน้อย / โฟกัสไม่ตรง / มือสั่น / เอียง 25° / ถือไกล / ถ่ายภาพนิ่ง 12MP
  ทุกภาพมีพื้นโต๊ะ ของวางรอบ ๆ หัวกระดาษกับเลขหน้า vignette noise และการบีบอัด JPEG
- **วัดผลด้วย CER** = (ตัวที่ผิด + ตัวที่หาย + ตัวที่เกินมา) ÷ จำนวนตัวอักษรจริง โดยไม่นับช่องว่าง
- **จำลองวิดีโอ** (`policy.py`): ยกกล้อง → ถือนิ่ง → ย้ายไปหน้าถัดไป → นิ่ง ทั้งหมด 10 ชุด (20 หน้า)
  สมมติให้ OCR บนมือถือใช้ 1–2.5 วินาที และ TTS พูดประมาณ 11 ตัวอักษรต่อวินาที

## สิ่งที่พบ (เรียงตามผลกระทบ)

### 1. แสงไม่สม่ำเสมอทำให้ OCR "มองไม่เห็น" ข้อความ
โหมดแบ่งหน้าอัตโนมัติ (PSM 3) ตีความภาพที่มีเงาหรือขอบมืดว่าเป็น "รูปภาพ" แล้วตัดทิ้งทั้งก้อน
ผลคือ 27% ของภาพได้ค่าว่าง ส่วนการครอปเฉพาะกรอบอย่างเดียวทำให้แย่ลงเป็น 66%
**แก้:** หารภาพด้วยสีกระดาษที่ประมาณได้ (flat-field) ทำให้พื้นขาวสม่ำเสมอ ช่วยได้มากที่สุดในการทดลองนี้
กรณีเงาพาด CER ลดจาก 39% → 1.5%

### 2. อ่านข้อความนอกเรื่องเข้ามาด้วย
อ่านทั้งเฟรม จึงได้ "หน้า 47", "แบบฝึกหัดท้ายบท" ปนมาด้วย
**แก้:** มีกรอบนำสายตาบนจอ และอ่านเฉพาะในกรอบ (กลางจอ 80% × 60%)

### 3. ขนาดตัวอักษรไม่พอดีกับ OCR
ตัวเล็กเกิน (ถือไกล, กล้องความละเอียดต่ำ) → อ่านผิด ตัวใหญ่เกิน → วรรณยุกต์หลุดไปเป็นบรรทัดขยะ เช่น "ะ ส ว"
**แก้:** วัดความสูงตัวอักษรจากก้อนหมึก แล้วย่อหรือขยายให้สูงประมาณ 28 px
(ทดลองค่า 20 / 28 / 36 แล้ว 28 ดีที่สุด)

| สถานการณ์ | เดิม | ใหม่ |
|---|---|---|
| ปกติ 1080p | 44.9% | 1.8% |
| กล้อง 640×480 | 44.3% | 1.4% |
| เงาพาด | 38.8% | 1.5% |
| แสงน้อย | 25.9% | 1.7% |
| โฟกัสไม่ตรง | 72.6% | 21.7% |
| มือสั่น | 99.5% | 92.8% ← ต้องแก้ด้วยการ "ไม่อ่าน" (ข้อ 6) |
| เอียง 25° | 43.1% | 0.6% |
| ถือไกล | 36.0% | 1.5% |

### 4. ลด noise / เพิ่มความคม ต้องเลือกใช้ตามสภาพภาพ
- ลด noise ช่วยตอนแสงน้อย (31% → 7%) แต่ทำให้ภาพความละเอียดต่ำแย่ลง (10% → 46%)
- เพิ่มความคมช่วยตอนโฟกัสไม่ตรง (25% → 18%) แต่ทำให้ภาพแสงน้อยพังหมด (100%)

**แก้:** วัด noise ของภาพก่อน ถ้า noise สูงให้ลด noise ถ้าไม่สูงให้เพิ่มความคม

### 5. โหมด OCR และการกรองผลลัพธ์
- PSM 6 (ข้อความเป็นก้อนเดียว) ดีที่สุดเมื่อใช้คู่กับการครอปกรอบ (PSM 3 / 4 / 6 / 11 ได้ 23.1 / 22.0 / 15.5 / 17.8%)
- ทิ้งบรรทัดที่มีตัวหลักน้อยกว่า 3 ตัว หรือความมั่นใจต่ำกว่า 60 → ขยะที่ TTS จะพูดเหลือ 0.1%
- โมเดล `best` แม่นกว่าเล็กน้อย (13.9 vs 15.5%) แต่ไฟล์ใหญ่ 22 MB เทียบกับ 6 MB และช้ากว่า 35% จึงใช้ `best_int` ตัวเดิม

### 6. "รีบอ่านเกินไป": อ่านตอนกล้องยังไม่นิ่ง
แบบเดิม OCR ทุก 2.5 วินาทีไม่ว่าภาพจะเป็นอย่างไร จึงมักไปจับเฟรมที่กำลังขยับ แล้วพูดข้อความมั่วยาวหลายวินาที

| นโยบาย (OCR 1.5 วินาที) | พูด | ถูก | มั่ว | หน้าที่อ่านถูก |
|---|---|---|---|---|
| เดิม: ทุก 2.5 วินาที | 14 | 5 | 6 | 5/20 |
| รอภาพคม (เฟรมเดียว) | 21 | 13 | 5 | 13/20 |
| **รอภาพนิ่ง 2 เฟรมติดกัน** | 17 | 17 | **0** | **17/20** |
| รอภาพนิ่ง + ผล OCR ตรงกัน 2 ครั้ง | 11 | 10 | 0 | 10/20 |

ถ้าใช้เกณฑ์ความคมแค่เฟรมเดียว เฟรม "กำลังจะนิ่ง" ซึ่งยังเบลออยู่จะผ่านเกณฑ์ แล้วได้ข้อความผิด
เกณฑ์ที่ใช้จริงคือ "ความคม ≥ ครึ่งหนึ่งของค่าสูงสุดใน 5 วินาทีล่าสุด และ 2 เฟรมติดกันความคมต่างกันไม่เกิน 35%"
ผลนี้คงที่ทั้งเมื่อ OCR ใช้ 1.0, 1.5 และ 2.5 วินาที

## สิ่งที่แก้ในเว็บ (`docs/`)

1. `preprocess.js` (ใหม่): ครอปกรอบ → วัด noise → ลด noise หรือเพิ่มความคม → ปรับขนาดตัวอักษร → ลบเงา → กรองบรรทัดขยะ
2. กรอบนำสายตาบนจอ ขึ้นเป็นสีเขียวเมื่อภาพนิ่งพอ
3. "อ่านเลย" รอให้ภาพนิ่งก่อน (สูงสุด 3 วินาที) / "อ่านอัตโนมัติ" อ่านเฉพาะตอนภาพนิ่ง 2 เฟรมติดกัน
4. คำแนะนำด้วยเสียง เช่น "ตัวหนังสือเล็กเกินไป ลองเลื่อนกล้องเข้าใกล้", "ถือกล้องให้นิ่ง"
5. เสียง: ช้าลง (0.8), อ่านทีละบรรทัดมีจังหวะหยุด, เลือกภาษาให้แต่ละบรรทัด, เลือกเสียงไทยในเครื่อง,
   และแจ้งเตือนถ้าเครื่องไม่มีเสียงภาษาไทย (ถ้าไม่มี Android จะอ่านภาษาไทยด้วยเสียงอังกฤษ ฟังไม่รู้เรื่อง)
6. ปุ่มไฟฉาย (ถ้ามือถือรองรับ) + ขอโฟกัสอัตโนมัติต่อเนื่อง

## รอบ 2: ภาพจริงจากมือถือ (การ์ด "สั่งอาหารยังไงให้สมดุล?")

ผู้ใช้ทดสอบจริงแล้วได้ข้อความขยะ เช่น "งเลไวโช | 0 ' 2 os % คว: เณ" ซึ่ง TTS ก็พูดออกมาทั้งที่ความมั่นใจแค่ 41%

**สาเหตุ:** ถือมือถือแนวตั้งถ่ายการ์ดแนวนอน **ตัวหนังสือจึงหมุน 90°** แต่ OCR อ่านได้แค่แนวนอน
และไม่มีตัวกรองที่บอกได้ว่าผลลัพธ์เป็นภาษาไทยจริงหรือเป็นขยะ

| มุมที่หมุน | ความมั่นใจของ OCR | ผล |
|---|---|---|
| 0° (แบบเดิม) | 54 | `/ % c 2 wn ;` |
| 90° | 65 | ขยะภาษาไทย ("รอทกงน ๐ลงางทกรถ…") |
| **270°** | 70 | **"สั่งอาหารยังไงให้สมดุล / ข้าวพอดี / เพิ่มผักหลากสี / เลือกโปรตีน… / ก็ดีขึ้นได้"** |

ความมั่นใจของ OCR แยกมุมที่ถูกกับมุมที่ผิดได้ไม่ชัด (70 เทียบกับ 65) จึงเพิ่ม 2 อย่าง

1. **ตัวตรวจทิศทางตัวหนังสือ** (projection profile): บรรทัดตัวหนังสือทำให้ผลรวมหมึกรายแถวขึ้นลงเป็นจังหวะ
   ตรวจถูก 4/4 มุมกับการ์ดจริง, ภาพจำลองแนวนอนไม่ถูกตีเป็นแนวตั้งเลย (0/100), ภาพจำลองที่หมุน 90° ตรวจเจอว่าเป็นแนวตั้งครบ 100/100
2. **โมเดลภาษาไทยระดับตัวอักษร** (`docs/thai-lm.js`, trigram 70 KB สร้างจากความถี่คำ Thai National Corpus ด้วย `build_lm.py`)
   ข้อความไทยจริงได้ประมาณ −3.5 ถึง −5 บิตต่อตัวอักษร ขยะได้ −6.2 ถึง −8.7
   ใช้เลือกมุมที่ถูก, ทิ้งบรรทัดขยะ, และ**ไม่พูด**เมื่อทั้งภาพเป็นขยะ

นอกจากนี้ได้เพิ่ม
- ตัดสัญลักษณ์และตัวอักษรเดี่ยวที่เรียงกันก่อนส่งให้ TTS
- แปลง "08.30 - 16.30 น." เป็น "08.30 ถึง 16.30 นาฬิกา"
- ลดขนาดตัวอักษรเป้าหมายจาก 28 เป็น 20 px: ภาพจำลอง (ไม่นับมือสั่น) CER 3.1% อ่านรู้เรื่อง 94% (เดิม 3.5% / 89%) และเร็วขึ้นประมาณ 25–35%
  วัดโดยเทียบกับคำตอบที่ผ่านกฎทำความสะอาดชุดเดียวกัน และไม่นับเครื่องหมายวรรคตอน

## ข้อจำกัด

- เป็นภาพจำลอง ไม่ใช่ภาพจากกล้องจริง: ไม่มีแสงสะท้อนบนกระดาษมัน หน้าหนังสือโค้ง หรือตัวหนังสือบนพื้นสี
- ยังวัดคุณภาพเสียง TTS ไม่ได้ เพราะขึ้นกับเสียงที่ติดตั้งในมือถือแต่ละเครื่อง
- ความเร็วที่วัดได้มาจากคอมพิวเตอร์ บนมือถือน่าจะช้ากว่า 3–5 เท่า (เตรียมภาพ ~1 วินาที + OCR ~1–2 วินาที)
- ตอนโฟกัสไม่ตรง (CER 22%) ยังแก้ด้วยโค้ดได้ไม่หมด ต้องให้ผู้ใช้ถอยกล้องหรือรอโฟกัส

## รันซ้ำ

```bash
npm install
node render_text.mjs           # เรนเดอร์ข้อความ
python -I sim.py scenes        # สร้างภาพจำลอง 100 ภาพ
python -I sim.py pipelines     # เตรียมภาพทุกวิธี
node ocr.mjs data/prep/manifest.json results/pipelines.json
python analyze.py results/pipelines.json pipelines
python -I sim.py sequence      # วิดีโอจำลอง
node make_seq_manifests.mjs     # สร้าง data/seq/m_p0.json, m_p9.json
node ocr.mjs data/seq/m_p0.json results/seq_p0.json --psm 3
node ocr.mjs data/seq/m_p9.json results/seq_p9.json --psm 6
python policy.py
node validate_js.mjs results/js_p9.json 6   # ยืนยันโค้ดจริงของเว็บ
```
